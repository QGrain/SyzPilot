# SyzTokenizer v3 & SyzEncoder Pretraining: Design, Implementation, and Results

> This document records the complete pipeline for training SyzTokenizer (a custom BPE tokenizer for syz-programs) and SyzEncoder (a domain-specific code encoder via MLM continue-pretraining). All content is organized for potential inclusion in academic publications.

---

## 1. Overview

The SyzPilot project requires a high-quality language model for syz-programs (the programs generated by the syzkaller kernel fuzzer). The pipeline consists of two stages:

1. **SyzTokenizer v3**: Train a custom BPE tokenizer that handles dirty fuzzing corpus gracefully (base64 padding, long repetitive runs, raw bytes) without polluting the vocabulary with garbage megatokens.
2. **SyzEncoder**: Continue-pretrain StarEncoder (a 124M RoBERTa-based encoder) on 2.2M syz-programs using MLM, with the custom tokenizer.

Both components were trained on a server with 3x NVIDIA A800 80GB GPUs. The pretraining used 2x A800-PCIe cards (cuda0 and cuda2), with GPU clocks locked at 1275 MHz (~90% of max) to manage temperature.

---

## 2. SyzTokenizer v3

### 2.1 Motivation and Problem

The original tokenizer training script (`train_tokenizer.py`) fed raw fuzzing program text directly to BPE, which caused severe vocabulary pollution:

- **Base64 padding blocks**: Long sequences of `AAAA...` or `====...` were learned as single megatokens (thousands of characters long).
- **Raw byte dumps**: Hexadecimal runs from `syz_mount_image` and other syscalls produced meaningless long tokens.
- **Old 300w tokenizer**: Resulted in a 429MB vocabulary file (vs. ~2MB for a healthy one), rendering it unusable for downstream tasks.

### 2.2 Design and Implementation

**File**: `filter/train_tokenizer_v3.py`

#### 2.2.1 Dirty-Data Cleaning (Pre-BPE Normalization)

Before BPE training, each program text undergoes two-stage normalization:

**Stage 1: Repetitive Character Compression**

```python
text = re.sub(
    r'(.)\1{REPEAT_COMPRESS_LEN,}',
    lambda m: m.group(1) * REPEAT_COMPRESS_LEN,
    text
)
```

Any sequence of `N+1` identical characters (where `N = repeat_compress_len`, default 32) is truncated to exactly `N` characters. This eliminates base64 padding blocks and runaway repetitive noise while preserving reasonable-length string literals.

**Stage 2: Bare Hex Run Compression (Optional)**

```python
text = re.sub(
    r'(?<![0-9a-fA-FxX])([0-9a-fA-F]{HEX_RUN_COMPRESS_LEN,})(?![0-9a-fA-F])',
    lambda m: m.group(1)[:HEX_RUN_COMPRESS_LEN],
    text
)
```

**Critical design decision**: The negative lookbehind `(?<![0-9a-fA-FxX])` ensures strings starting with `0x` (e.g., `0x7f0000002000`) are **never** compressed. Only bare hex runs (long hashes, raw bytes without `0x` prefix) are truncated to the first `hex_run_compress_len` characters. This was verified empirically.

#### 2.2.2 BPE Token Length Limit

`max_token_length = 64` is passed to `GPT2TokenizerFast.train_new_from_iterator()`, preventing BPE from merging subwords into tokens longer than 64 characters. This acts as a hard ceiling against any residual dirty data that evades the regex cleaners.

#### 2.2.3 Multiprocessing Optimization (v3)

Tokenizer training is CPU-bound (file I/O + regex normalization). v3 introduces `multiprocessing.Pool` with 32 workers:

```python
with Pool(processes=workers,
          initializer=_worker_init,
          initargs=(rcl, chr_flag, hcl)) as pool:
    for content in pool.imap_unordered(_worker_process, files, chunksize=100):
        ...
```

- `chunksize=100` reduces IPC overhead for ~2.2M small files.
- Workers are initialized once with cleaning parameters via `_worker_init`.
- Achieved **~10x speedup** on 224w dataset (v2: ~4 min; v3: ~25 sec for file reading) and **~3.7x** on 300w (v2: ~94 min; v3: ~25 min).

#### 2.2.4 Special Tokens Route (Rejected)

An alternative route injecting ~66 high-frequency syscall names as `new_special_tokens` was evaluated. Results showed the base route (no special tokens) outperformed the special route in **all** 12 (dataset, size) combinations. BPE naturally segments syscall names into reasonable subwords (e.g., `ioctl$KVM_CREATE` -> `ioctl` + `$` + `KVM` + `CREATE`), making explicit injection unnecessary and counterproductive.

### 2.3 Datasets

| Dataset | Size | Source | Characteristics |
|---------|------|--------|-----------------|
| **dataset_224w** | 2,236,878 programs | Pure v6 Linux kernel fuzzing corpus | Clean, consistent syntax, minimal raw bytes |
| prog_dataset_300w | ~3M programs | Cross-version (v5.15, v6.6, v6.12) | Contains raw bytes, base64 dumps, noisier |

**Downstream validation proved 224w significantly outperforms 300w** (MLM val loss 1.16 vs 2.37). Therefore, 224w was selected for the final tokenizer and encoder training.

### 2.4 Hyperparameter Grid Search

**File**: `filter/run_tokenizer_search.py`

A systematic grid search was conducted to find optimal tokenizer cleaning parameters.

**Search space**:
- 2 datasets: 224w, 300w
- 3 sample sizes: 10k, 50k, 100k
- 2 routes: base (no special tokens), special (~66 syscall names)
- 27 parameter combos:
  - `repeat_compress_len`: {16, 32, 64}
  - `max_token_length`: {32, 64, 128}
  - `compress_hex_runs`: {True, False}
  - `hex_run_compress_len`: {8, 16} (only meaningful when chr=True)

**Total**: 2 x 3 x 2 x 27 = **324 experiments**, running in parallel on CPU via `ProcessPoolExecutor`.

**Key findings**:

| Metric | 224w | 300w | Base Route | Special Route |
|--------|------|------|-----------|---------------|
| Mean Composite Score | **0.7114** | 0.6754 | **0.6991** | 0.6876 |

- **Best base params** (highest composite score = 0.7220):
  - `repeat_compress_len = 32`
  - `max_token_length = 64`
  - `compress_hex_runs = True`
  - `hex_run_compress_len = 8`

### 2.5 Downstream Validation (MLM as Gold Standard)

**File**: `filter/run_downstream_validation.py`

Static benchmark scores can be misleading. The final tokenizer selection was validated via **small-scale MLM pretraining** comparing 4 candidates:

| ID | Dataset | Params | MLM Val Loss |
|----|---------|--------|-------------|
| A | 224w | Best (rcl=32, mtl=64, chr=1, hcl=8) | **1.1556** |
| B | 224w | Worst (hcl=16) | 1.1982 |
| C | 300w | Best | 2.4473 |
| D | 300w | Worst | 2.3671 |

**Conclusions**:
1. 224w consistently outperforms 300w regardless of tokenizer params (dataset quality dominates).
2. On clean data (224w), static score correlates with MLM performance (best > worst).
3. On dirty data (300w), the relationship inverts: "worst" static params achieve better MLM loss than "best". Over-aggressive cleaning removes useful context.
4. **Winner: A_224w_best**.

### 2.6 Final Training

**Command**:
```bash
python train_tokenizer_v3.py \
  --dataset /artifact/datasets/dataset_224w/programs \
  --base_model /opt/syzpilot/models/starencoder \
```

**Results**:

- Output vocab size: 49,152

## 3. SyzEncoder

### 3.1 Base Model Selection

**Model**: StarEncoder (HuggingFace `bigcode/starencoder`)
- Architecture: RoBERTa-based, 124M parameters
- Pretraining: MLM on 1TB of Python + Java + JavaScript code
- Vocab size: 49,156 (we resize to 49,152 to match SyzTokenizer)
- Why: Strong code understanding + manageable size for continue pretraining on a single server

### 3.2 Training Paradigm

**Continue Pretraining with Masked Language Modeling (MLM)**:
- Masking probability: 15%
- Masking strategy: 80% [MASK], 10% random token, 10% keep original (standard BERT MLM)
- Max sequence length: 1024
- Padding: `longest` (dynamic, capped at 1024 via `truncation=True`)

### 3.3 Code Implementation and Key Fixes

**File**: `filter/pretrain_encoder_mlm.py`

The original implementation had several issues that would compromise training quality. Nine fixes were applied before full-scale training:

| # | Issue | Impact | Fix |
|---|-------|--------|-----|
| 1 | Val dataloader `shuffle=True` | Inconsistent evaluation samples across checkpoints, val loss not strictly comparable | `shuffle=False` |
| 2 | Missing `accelerator.accumulate()` | `gradient_acc_step > 1` completely ineffective | Wrap train step in `with accelerator.accumulate(model):` |
| 3 | `padding="max_length"` | Wastes compute on padding tokens for short programs | `padding="longest"` |
| 4 | Weight decay on bias/LayerNorm | Over-regularization harms convergence | Group parameters: `no_decay=["bias", "LayerNorm.weight"]` |
| 5 | `evaluate_model` reuses old iterator | Evaluates from arbitrary offset, sample coverage unstable | Reset `val_dataiter = iter(val_dataloader)` at each eval call |
| 6 | No checkpoint cleanup | Disk usage grows linearly with saves | `_cleanup_old_checkpoints(keep=5)` |
| 7 | `save_interval=500` | Produces ~378 checkpoints over 3 epochs, unmanageable | `save_interval=6000` (~32 saves total) |
| 8 | Early stopping `patience=3` | Too tight for 3-epoch short training; may truncate prematurely | Removed entirely; train through all 3 epochs |
| 9 | `session_name` default `syzencoder_300w` | Misleading directory names if not overridden | Default changed to `default_session` |

### 3.4 Hyperparameter Configuration

| Parameter | Value | Rationale |
|-----------|-------|-----------|
| Epochs | 3 | Continue pretraining standard; enough to adapt to domain without catastrophic forgetting |
| Batch size (per GPU) | 32 | Fits in ~31GB of 80GB A800 with safety margin |
| Gradient accumulation | 1 | Effective global batch = 32 x 2 GPUs = **64** |
| Learning rate | 2e-5 | Conservative for continue pretraining (smaller than from-scratch) |
| Weight decay | 0.01 | BERT-family standard; bias/LayerNorm excluded |
| Warmup | 5% of total steps | Cosine schedule with gentle warmup |
| Max grad norm | 1.0 | Standard clipping |
| MLM probability | 0.15 | BERT default |
| Save interval | 6,000 steps | ~31 checkpoints + final over 3 epochs |
| Test steps | 200 | 200 x 64 = 12,800 val samples (~5.7% coverage), stable estimate |

#### 3.6.3 Convergence Analysis

The training exhibits **normal convergence** without overfitting:

1. **Monotonic val loss decrease**: The final checkpoint (step 90,000) achieves the lowest val loss across all 15 evaluation points.
2. **Mid-training plateau (steps 42k-60k)**: Val loss stalls around 0.83 with minor fluctuations. This is a typical artifact of cosine LR schedule -- as LR remains relatively high in the mid-phase, the optimizer oscillates in a flat loss landscape. As LR decays toward zero in the final epoch, fine-grained convergence resumes (steps 66k-90k show consistent improvement).
3. **No overfitting signal**: Val loss never exhibits two consecutive significant increases. Training loss continues to decrease alongside val loss, indicating the model has not memorized the training set.
4. **Training loss volatility** is expected for MLM: each batch masks a random 15% of tokens, and the difficulty of masked positions varies significantly across batches.

#### 3.6.4 Checkpoint Quality

The `best_model` directory contains the encoder checkpoint from **step 90,000** (lowest val loss). The `final_syzencoder` directory contains the checkpoint after the full 3 epochs. Both are saved in HuggingFace format (config.json + model.safetensors + tokenizer files).

## 4. Evaluation Hierarchy and Best Practices

The following hierarchy was established and validated during this project:

1. **Sanity Check**: Detect vocab pollution, abnormal token sizes, file bloat (e.g., 429MB vocab = failure).
2. **Static Benchmark**: CPT, truncation rate, syntax-aware metrics. Useful for screening but **not a final verdict**.
3. **Downstream MLM Validation**: Small-scale pretraining comparing MLM val loss across tokenizer candidates. **Strong proxy for quality**.
4. **Extrinsic Evaluation (TODO)**: Fine-tune on reach classification (`train_v2.py`) and compare accuracy/F1 against StarEncoder baseline. **Gold standard**.

**Key lesson**: Static composite scores can be misleading, especially on dirty data (300w). The 300w "worst" static params outperformed "best" params in MLM validation, because over-aggressive cleaning removes useful context. **Always validate tokenizers via downstream MLM loss before final selection.**

```bash
cd /opt/syzpilot/filter
export PYTORCH_CUDA_ALLOC_CONF="expandable_segments:True"
export TOKENIZERS_PARALLELISM=false
accelerate launch pretrain_encoder_mlm.py \
  --prog_dataset /artifact/datasets/dataset_224w/programs \
  --base_model /opt/syzpilot/models/starencoder \
  --tokenizer /opt/syzpilot/models/SyzTokenizer_224w \

  --max_grad_norm 1.0 --mlm_probability 0.15 \
  --save_interval 6000 --test_steps 200 \
```
